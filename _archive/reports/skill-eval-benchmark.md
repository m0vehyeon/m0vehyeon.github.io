**저장소**: [github.com/m0vehyeon/skill-eval-benchmark](https://github.com/m0vehyeon/skill-eval-benchmark)
**측정 대상**: 실제 로컬 환경에 설치된 서드파티 Agent Skill 8종 (이미지/영상 생성 5종, 애니메이션 1종, 브라우저 자동화 1종, 문서 조회 1종)
**관점**: 스킬 자체가 아니라 **벤치마크 설계·구축·실행** 능력을 증명하는 산출물이다. 측정 대상 스킬은 전부 원저작자의 것이며, 이 리포트와 저장소는 그 콘텐츠를 재배포하지 않는다.

---

## 왜 이 벤치마크가 필요한가

[OpenHands SDK 분석](/reports/openhands-sdk-analysis)에서 다룬 비판 중 하나가 "압축 품질을 검증하는 장치가 없다"는 것이었다. 같은 문제가 Skill 시스템에도 있다 — **스킬이 의도한 대로 발동·라우팅되는지 확인하는 장치 없이 스킬 개수만 늘어나는 경우**가 많다. 담당 업무가 "Agent의 성능과 한계를 체계적으로 측정하기 위한 Benchmark를 설계·구축"이므로, 비판만 하지 않고 직접 만들었다.

---

## 4계층 설계

| 계층 | 측정 질문 |
|---|---|
| **trigger** | 발동해야 할 때 발동하는가 / 하지 말아야 할 때 안 하는가 |
| **routing** | 서로 겹치는 스킬 여러 개 중 올바른 것을 고르는가 |
| **reference-loading** | 스킬 본문을 연 뒤, 필요한 참조 파일만 읽는가 (점진적 공개 준수) |
| **output rubric** | 스킬을 고른 이후의 행동 품질 (정성 평가) |

측정 대상은 8종이다. 그중 5종(Higgsfield 계열: generate/marketplace-cards/product-photoshoot/soul-id/websites)은 서로 인접한 도메인이라 **routing 레이어의 진짜 시험대**가 된다 — 각 스킬의 설명에는 "NOT for: X (use Y)" 형태의 명시적 경계가 있어서, 정답이 임의로 정한 게 아니라 스킬 자신의 정의에서 도출된다.

## 안전 설계 — 실제 과금 없이 라우팅 결정만 관찰하기

측정 대상 스킬 다수는 내부적으로 `Bash`를 통해 실제 유료 API를 호출한다. 벤치마크가 실행 중 진짜 이미지·영상을 생성하면 안 되므로, 실행기는 `Bash`를 도구 목록에서 완전히 제거한다(`--disallowedTools`) — 권한 프롬프트를 막는 게 아니라, 모델이 그 도구를 **요청하는 것 자체가 불가능**하게 만든다. `--permission-mode bypassPermissions`는 이 차단 위에서 Read/Glob 같은 무해한 도구의 승인 프롬프트만 생략하는 용도다.

이 설계 덕분에 "어느 스킬을 어떤 파라미터로 호출하려 했는가"까지는 정확히 관찰되고, 그 다음(실제 API 호출)은 항상 안전하게 막힌다 — 측정 대상과 부작용이 구조적으로 분리된다.

## 신호 추출 — 스킬 호출은 어떻게 관측되는가

`claude -p --output-format stream-json`으로 실행하면 매 이벤트가 JSON 한 줄로 스트리밍된다. 스킬이 실제로 호출되면 `Skill` 이름의 `tool_use` 블록에 호출된 스킬 이름이 그대로 담긴다:

```json
{"type": "tool_use", "name": "Skill", "input": {"skill": "higgsfield-product-photoshoot", "args": "..."}}
```

이 필드 하나가 trigger·routing 레이어의 채점 기준이다. `Read` 도구 호출의 `file_path`를 모아서 `references/` 하위 경로만 남기면 reference-loading 레이어가 된다.

## 결과

58개 케이스, 총 비용 $6.40.

| 계층 | pass/total |
|---|---|
| trigger | 28/34 (82.4%) |
| routing | 10/14 (71.4%) |
| reference-loading | 5/10 (50.0%) |

숫자만 보면 낮아 보인다. 그런데 실패 15건을 트랜스크립트 단위로 직접 읽어보면 그중 **13건(87%)이 라우팅 오류가 아니라 "정보가 부족해서 스킬을 아예 시도하지 않고 되물은 것"** 이었다. 예를 들어 "내 폰케이스 사진으로 라이프스타일 이미지를 만들어줘"라는 프롬프트에 스킬을 고르는 대신 "사진을 공유해 주실 수 있나요?"라고 되물은 경우다. 이건 정보 없이 추측하지 않는 바람직한 행동이지, 스킬 선택이 틀린 게 아니다 — 다만 이 벤치마크가 단일 턴이라 "정보를 받은 뒤 무엇을 골랐을지"는 관찰 범위 밖이다.

이 13건을 "판단 보류"로 분리하면: **실제로 스킬 결정을 시도한 45건 중 44건이 정확했다 (97.8%).**

### 벤치마크 설계 자체에 대한 교훈

단일 턴 eval은 "틀렸다"와 "정보가 부족해 판단을 보류했다"를 같은 fail 라벨로 뭉갠다. 스킬 라우팅 벤치마크를 설계한다면 처음부터 **"적절하게 판단을 보류함"** 을 세 번째 라벨로 넣어야 한다는 게 이번 작업에서 얻은 가장 실질적인 결론이다.

### 진짜 라우팅 미스 1건 — 일반 지식이 스킬을 가린다

"사이트를 배포하기 전에 확인할 SEO 체크리스트가 뭐야?"라는 질문에는 스킬을 호출하지 않고 모델이 가진 일반적인 SEO 지식으로 바로 답했다. 질문이 플랫폼 맥락 없이도 답할 수 있을 만큼 일반적으로 들리면, 모델이 스킬 특화 참조보다 자기 지식을 먼저 쓸 수 있다는 뜻이다. 스킬의 존재 이유가 "일반론보다 이 플랫폼에 특화된 답"이라면, 트리거 문구가 일반론처럼 들리는 질문까지 확실히 잡아채도록 설계돼야 한다는 교훈이다.

### 참조 과다 로드 1건

"React 최신 문서를 에이전트 컨텍스트로 가져오는 법"이라는 질문에는 정답 참조(`docs.md`)를 정확히 읽었지만, 무관한 초기 설정 가이드(`setup.md`)도 함께 읽었다. 필요한 것만 읽는 데는 성공했지만 필요하지 않은 것도 안 읽는 데는 실패한 사례 — reference-loading 레이어가 잡아내라고 설계된 정확히 그 종류의 결함이다.

### 카탈로그 오염 — 별도로 관측한 현상

정식 채점에 들어가지 않은 파일럿 단계에서, 같은 프롬프트("분기별 매출 성장 바 차트를 애니메이션으로")가 대상 스킬이 아니라 **환경에 함께 로드돼 있던 무관한 스킬**을 호출한 적이 있다. 정식 채점에서 같은 프롬프트를 다시 실행했을 때는 이 미스라우팅이 재현되지 않고 대신 정보 부족으로 되물었다 — 동일 입력에 대해 실행마다 다른 경로를 타는 비결정성을 직접 관측했다. 이 픽스처가 대상 8종 외에도 실행 환경의 다른 스킬들과 카탈로그를 공유한 상태였다는 걸 감안하면, **스킬 카탈로그가 넓어질수록 라우팅이 무관한 후보와도 경쟁해야 한다**는 실무적 시사점으로 남긴다. [OpenHands SDK 분석](/reports/openhands-sdk-analysis)에서 짚은 "이름 충돌이 로드 순서에 의존한다"는 관찰과 같은 계열의 문제다.

## 한계

- **n=1 per case** — 케이스당 1회만 실행했다. 위에서 보듯 같은 프롬프트도 실행마다 다른 경로를 탈 수 있어, 통계적으로 견고한 버전은 케이스당 반복 실행 후 비율로 보고해야 한다
- **스킬 카탈로그 격리가 완전하지 않았다** — 실행 환경의 다른 스킬들이 픽스처에 함께 노출됐다
- **output rubric 레이어는 자동 채점이 아니라 정성 평가 기준만 마련**했고, 이번 라운드에서 표본 채점까지는 하지 못했다
- **단일 턴 한정** — 명확화 질문에 답한 뒤의 행동은 관찰 범위 밖이다

전체 코퍼스·실행기 코드·원본 결과는 [저장소](https://github.com/m0vehyeon/skill-eval-benchmark)에 있다.
