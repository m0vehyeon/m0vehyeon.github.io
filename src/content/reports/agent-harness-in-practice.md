**대상**: Daeng — Claude Code와 Codex를 병행해 개발한 개인 프로젝트 (pnpm 모노레포, React Native/Expo + Supabase). 5주간 434커밋, 스펙 49건·플랜 53건.
**관점**: 코딩 에이전트를 도구로 "쓰는" 경험이 아니라, 에이전트가 실패하는 지점을 관측하고 그걸 어떤 계층으로 옮겨 교정했는지의 기록.
**비고**: 저장소는 현재 비공개다. 이 글은 링크 대신 설계 판단과 코드 발췌 인용으로 구성한다.

## 왜 "활용"이 아니라 "교정"인가

코딩 에이전트를 오래 쓰다 보면 반복되는 패턴이 하나 있다. **프롬프트로 준 지시는 지켜지지 않는다.** 한 번은 지켜지고, 세션이 바뀌거나 컨텍스트가 압축되거나 다른 에이전트가 같은 저장소를 건드리는 순간 다시 어긋난다.

이 관찰이 이 글 전체의 전제다. 아래 네 가지는 전부 "프롬프트로 말했는데 왜 안 지켜지지?"라는 질문에서 시작해서, 그 규칙을 프롬프트보다 강제력이 센 계층 — 파일 구조, git 훅, 재시도 예산, 보고 의무 — 으로 옮긴 기록이다.

## 1. 지침을 계층으로 나눈 이유와 구조

### 문제

에이전트 지침 파일(`AGENTS.md`)이 하나만 있으면 두 가지가 섞인다. **저장소 전역에 항상 적용되는 계약**(커밋 컨벤션, 브랜치 정책)과 **특정 패키지에서만 의미 있는 규칙**(예: Supabase 마이그레이션 절차)이 한 파일에 누적되면, 매 세션이 관련 없는 수천 줄을 읽고 시작하게 된다. 컨텍스트 예산 문제다.

동시에 안정적인 정책(규칙)과 변하는 상태(지금 어떤 작업이 진행 중인지)가 같은 파일에 섞이면 diff가 지저분해지고, 규칙을 찾기 위해 상태 이력을 헤쳐야 한다.

이 두 문제를 해결하기 위해 **별도 스펙 문서를 써서 지침 재구조화 자체를 설계 대상으로 다뤘다.** 스펙에 명시한 해결 대상:

- "필수 독서 목록이 모든 에이전트를 관련 없는 수천 줄로 통과시킨다" — 컨텍스트 예산
- 안정 정책과 히스토리컬 상태의 혼재 — static rules vs dynamic state 분리 필요
- 규칙 간 모순 (예: dev→main 절차와 "항상 main 워크트리 고정" 규칙이 동시에 존재)
- 완료 장부(ledger)가 두 워크트리의 작업 중복을 막지 못함
- 머신 종속 경로가 정책 파일에 박혀 있어 이식성이 떨어짐

### 해결

- 루트 `AGENTS.md`에는 **저장소 전역 계약만** 남기고, 패키지별 스코프 지침을 5곳(`apps/mobile/`, `apps/admin/`, `packages/analyzer/`, `packages/collector/`, `supabase/`)으로 분리했다. 규칙이 충돌하면 **가장 가까운 파일이 이긴다**는 우선순위를 명시해, 계층 간 모순 자체를 규칙으로 흡수했다.
- `CLAUDE.md`를 `AGENTS.md`의 심볼릭 링크로 구성했다. Claude Code와 Codex가 서로 다른 파일명을 관례로 쓰기 때문에, 도구별로 지침을 두 벌 관리하면 반드시 한쪽이 낡는다. **심볼릭 링크로 단일 소스를 두 도구에 동시에 주입**하는 쪽을 택했다.
- 안정 규칙(`AGENTS.md`)과 가변 진행 상태(별도 진행 로그 파일)를 분리했다. 이건 에이전트 아키텍처에서 말하는 **system prompt 계층과 memory 계층의 분리**와 같은 판단이다 — 항상 참인 것과 지금 참인 것을 같은 파일에 두지 않는다.

`AGENTS.md`는 이후 12회 이상 개정됐다. 처음부터 완성된 설계가 아니라, **실패를 만날 때마다 규칙을 덧대며 굳혀온 하네스**라는 뜻이다 (squash 정책, fast-forward 승격 조건, 워크트리 정리 절차, 이슈 종료 규칙, 작업 전 pull 규칙 등).

## 2. 프롬프트 지시를 기계 계층으로 옮긴 사례

### 문제

여러 에이전트(Claude Code, Codex)가 같은 clone을 공유하며 병렬로 작업할 때, 규칙은 "각자 워크트리에서 작업할 것"이었다. 그런데 프롬프트 지시만으로는 이게 지켜지지 않았다 — 누군가 주 워크트리에서 `git checkout`으로 브랜치를 바꾸면, 그 순간 다른 세션들의 HEAD까지 같이 틀어진다. 지시가 무시되는 게 아니라, **에이전트가 그 지시의 부작용 범위를 인지하지 못한 채 정상적인 작업으로서 checkout을 실행**하는 것이었다.

### 해결

이 문제를 프롬프트를 더 정교하게 쓰는 방식이 아니라, git 훅으로 옮겼다.

- `scripts/agent-worktree.sh` — 에이전트별 전용 워크트리를 생성하고, 의존성을 설치하고, 감시 훅을 활성화한다.
- `.githooks/post-checkout` — 주 워크트리에서 브랜치가 전환되면 경고를 띄운다.

이 훅에 남긴 주석이 이 사례의 핵심이다 (원문):

> 왜: 여러 에이전트(Codex/Claude 등)가 같은 clone을 공유할 때, 누군가 주 디렉토리에서 `git checkout`으로 브랜치를 바꾸면 나머지 세션의 HEAD까지 같이 튄다. 규칙은 "각자 워크트리에서 작업"이지만 지시가 무시되는 일이 잦아, 이 훅으로 최소한 감지·경고한다.
> 한계: git엔 checkout을 사전에 막는 pre-checkout 훅이 없다. ... 자동 되돌림은 다른 세션 작업을 깰 수 있어 일부러 안 함.

이 한 사례에 세 가지가 같이 들어 있다.

1. **구체적인 실패 모드를 관측했다** — "지시가 무시된다"가 아니라 정확히 "주 워크트리에서의 checkout이 다른 세션의 HEAD를 오염시킨다"까지 좁혔다.
2. **프롬프트로는 강제되지 않음을 인지하고 기계적 계층(git 훅)으로 옮겼다.**
3. **한계와 트레이드오프를 의도적으로 문서화했다.** git에는 pre-checkout 훅이 없어 사전 차단은 불가능하다 — 이건 감지만 가능하고 예방은 안 되는 완화책이라는 걸 숨기지 않았다. 그리고 자동 되돌림(auto-revert)을 넣지 않은 것도 실수가 아니라 **의도적 선택**이다: 되돌림이 다른 세션이 이미 진행 중인 작업을 깰 수 있기 때문이다.

하네스 엔지니어링에서 중요한 건 "막았다"가 아니라 **막을 수 없는 지점을 명시하고, 완화책의 부작용까지 계산해서 선택했다는 것**이라고 생각한다. 이 사례가 그 판단을 가장 압축적으로 보여준다.

## 3. 검증 루프 — 완료 선언을 신뢰할 수 있게 만들기

### 문제

에이전트는 작업을 끝냈다고 스스로 선언하는 데 낙관적이다. 테스트를 일부만 돌리고도 "완료"라고 보고하거나, 어떤 검사를 건너뛰었는지 말하지 않는 경우가 있다. 이 상태에서는 완료 선언 자체를 신뢰할 수 없다.

### 해결

작업 흐름을 spec → plan → task brief → 실행 → report → **review diff** 로 닫히는 루프로 고정했다.

- 스펙 49건, 플랜 53건이 5주간 쌓였다. 스펙은 "무엇을, 왜"를 고정하고 플랜은 "어떤 순서로"를 고정한다.
- 각 작업 단위마다 `task-N-brief.md` / `task-N-report.md` 쌍을 남기고, 커밋 구간별로 `review-<sha>..<sha>.diff`를 생성해 리뷰한다.
- `AGENTS.md`의 검증 게이트는 좁은 테스트 → 패키지 테스트/타입체크 → 전체 체크 → diff 공백 검사 순으로 단계를 명시하고, **"수행한 검사와 결과, 건너뛴 검사를 모두 보고할 것"** 을 규칙으로 못박았다.

이 마지막 규칙이 핵심이다. "테스트를 통과시켜라"는 결과를 요구하는 규칙이고, "무엇을 건너뛰었는지 보고하라"는 **정직성을 요구하는 규칙**이다. 전자만 있으면 에이전트는 실패한 검사를 조용히 생략하고 완료를 선언할 유인이 있다. 후자가 있어야 그 생략 자체가 리뷰 대상이 된다.

TDD도 같은 논리로 루프에 넣었다 — 실패하는 테스트를 먼저 쓰고, 실패를 확인하고, 최소 구현을 하고, 다시 돌린다. "테스트를 통과했다"가 아니라 "테스트가 먼저 실패하는 걸 확인했다"를 요구하는 것도 같은 종류의 정직성 강제다.

## 4. LLM 실패 복구 — 재시도 예산을 실제 장애 기반으로 분리

### 문제

이 프로젝트는 코딩 보조를 넘어 **제품 파이프라인 안에서 Claude를 subprocess로 호출**한다 (`spawn`으로 실행, 스크리닝 → 추출 → 판정의 구조화된 LLM 파이프라인). 이 경로에서 실제 운영 장애가 있었다: Claude가 이따금 문법적으로 깨진 JSON을 반환했고, 2026-07-24 스케줄 실행이 이 문제로 실패했다.

### 해결

코드에 남긴 주석이 원인과 대응을 함께 설명한다 (원문):

> Claude가 이따금 문법적으로 깨진 JSON을 반환한다(예: 배열 요소 사이 콤마 누락, 2026-07-24 스케줄 실행 실패 사례). 동일 프롬프트를 다시 물으면 대개 유효한 JSON이 나오므로, 파싱 실패 시 재시도한다. 각 시도가 LLM 호출이라 느려서(수 분~십수 분) 지수 백오프 없이 바로 재시도한다.

여기서 판단이 갈리는 지점이 두 개 있다.

**① 재시도 예산을 파싱 실패와 프로세스 실패로 분리했다.** JSON 파싱이 깨지는 것과 프로세스 자체가 죽는 것은 다른 실패이고, 다른 복구 전략이 필요하다. 이를 `CLAUDE_JSON_MAX_ATTEMPTS` / `CLAUDE_PROCESS_MAX_ATTEMPTS` / `CLAUDE_PROCESS_BASE_DELAY_MS`로 나눠 각각 예산을 두고, 이 값들을 단위 테스트로 고정했다.

**② 지수 백오프를 의도적으로 뺐다.** 일반적으로 재시도 전략이라 하면 지수 백오프가 기본값처럼 따라오지만, 여기서는 뺐다. 이유는 비용 구조에 있다 — 호출당 응답 시간이 수 분에서 십수 분이다. 이 스케일에서는 백오프로 버는 시간이 무의미하고, 오히려 재시도 자체의 지연이 커진다. **일반적으로 옳다고 여겨지는 패턴도 실제 비용 특성과 맞지 않으면 버린다**는 판단이 이 결정에 들어 있다.

## 요약

이 네 사례를 관통하는 하나의 판단이 있다.

**프롬프트에 쓴 지시는 규칙이 아니라 요청이다.** 실제로 지켜져야 하는 것은 파일 구조(계층형 지침), git 훅(워크트리 가드), 보고 의무(검증 루프), 재시도 예산(LLM 실패 복구)처럼 프롬프트보다 강제력이 있는 계층으로 옮겨야 한다.

그리고 그 계층으로 옮길 때마다, **막을 수 없는 지점과 트레이드오프를 같이 문서화했다** — pre-checkout 훅의 부재, 자동 되돌림을 넣지 않은 이유, 지수 백오프를 뺀 이유. 하네스는 "규칙을 강제하는 장치"만이 아니라 "어디까지 강제되고 어디부터는 안 되는지를 아는 장치"이기도 하다고 생각한다.
